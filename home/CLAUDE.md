# Куда писать то, что узнал по ходу

**Что узнал сам — в auto memory, не в `CLAUDE.md`.** Команда сборки, неочевидная
грабля, где что лежит, моя поправка по ходу разговора. Память живёт в
`~/.claude/projects/<репозиторий>/memory/`, ключуется по git-репозиторию (то есть общая
для всех воркtree одного проекта), в git проекта не попадает и коммита не требует.
Это основной маршрут: девять правок из десяти должны уходить сюда.

**В `CLAUDE.md` проекта — только то, что я подтвердил.** Конвенции, архитектура,
«всегда делай X». Считаешь, что правило созрело для переноса из памяти в `CLAUDE.md` —
предложи, молча не переноси.

Обвязка лежит в двух корнях. **Тулинг** (git) — `link.sh`, этот файл, шаблоны проекта;
путь — цель симлинка `~/.claude/CLAUDE.md`. **Данные** (без git) — каталог `$CLAUDE_DATA`,
по умолчанию `~/Documents/claude-config`: обвязка и вики проектов, память, журнал решений по
проектам. Ниже `<данные>` — корень данных.

`CLAUDE.md` проекта — симлинк в `<данные>/projects/<проект>/CLAUDE.md` (синк данных между
машинами, если он есть, — не твоё дело). Правь напрямую, разрешения на саму запись не
спрашивай — каталог прописан в `permissions.additionalDirectories`. Коммита не требует и
не версионируется git.

**История конкретной задачи — в вики задач, не в память.** Что просили, что и почему
сделали, какие грабли и что осталось — это документ задачи (раздел ниже), пополняется
командой `/save-task-context`.

**Решения по самой обвязке — в журнал решений, не в память проекта.** Зачем заведён
агент, скилл, хук или скрипт, почему такая модель/effort, что отвергли, когда поменяли —
`decisions/` (правила — его `CLAUDE.md`). Журналов два: решения по тулингу (`link.sh`,
этот файл, шаблоны) — в `decisions/` тулинга, по обвязке конкретных проектов — в
`<данные>/decisions/`. Меняешь обвязку — запиши решение в той же сессии, без спроса.
Спрашивают «зачем у нас X» — сначала `decisions/index.md` обоих.

# Задача по номеру — сначала её документ

Если у проекта есть вики задач (`<данные>/projects/<проект>/tasks/`),
то номер задачи в сообщении (`PROJ-123`, «123») — сигнал сначала прочитать
`tasks/pages/<номер>.md`, а не git и код. Если номер не назван («та задача про пустой
экран профиля»), документ ищется через `grep -ri` по `tasks/index.md` (в нём
заголовок тикета и ключевые слова), а если там не нашлось — по `tasks/pages/`.

- Вопрос «что, когда, почему сделали» — отвечаю по документу; в git и код иду, только
  если в документе нет ответа.
- Беру задачу в работу (новая, доработка после QA, продолжение) — сначала смотрю, нет ли
  уже документа по ней и по связанным задачам.
- Документ говорит, что и почему сделали на дату записи; код — что там сейчас.
  Расходятся — прав код, а документ дописываю.

Схема и формат документа — `tasks/CLAUDE.md`. Документ создаётся и пополняется
командой `/save-task-context`, которую ты вызываешь в конце сессии.

# Сначала вики проекта, потом код

Если у проекта есть локальная вики
(`<данные>/projects/<проект>/wiki/`) — она читается **первой**:
до Grep/Glob/Read по репозиторию, до плана и до вопросов мне «а где у вас лежит X».

Порядок в начале каждой задачи:

1. Прочитал `wiki/index.md` — это каталог страниц.
2. Прочитал подходящие `wiki/pages/<slug>.md` целиком.
3. Только потом пошёл в код — уже зная, куда смотреть.

Триггер — **не** «вопрос по архитектуре»: задачи так себя не называют, и правило
не срабатывает. Триггер простой: *собираюсь разбираться в незнакомой части
проекта*. «Добавь функциональность в фичу X», «почини Y в разделе Z», «как тут
устроен W» — всё сюда.

**Нет в вики страницы по теме — это не тупик, а работа.** Разбираешься по коду
как обычно, а потом дописываешь узнанное в вики (операция ingest, правила в
`wiki/CLAUDE.md`). Смысл вики в том, что она компаундируется: выясненное сегодня
в следующей сессии выяснять заново не нужно. Разрешения на правку вики не
спрашивай — она вне git, коммита не требует.

Вики не отменяет следующее правило, а встаёт перед ним: страница говорит, КУДА
смотреть и какие грабли уже известны; код, макет и API подтверждают, ЧТО там
сейчас. Расходятся — прав код, а страницу поправь.

# Перед реализацией — сверься с источником истины

Не планируй и не пиши код по памяти или догадкам. Сначала открой фактический
источник истины и подтверди по нему конкретику:

- **UI по дизайну** — открой сам макет (Figma MCP: `get_design_context`,
  `get_screenshot`, `get_variable_defs`), а не описывай его «как обычно бывает».
- **Работа с API** — смотри реальный ответ (пример JSON, прокси-оверрайд,
  существующий data-класс/маппер), а не выдумывай поля и флаги. Ловил тебя на том,
  что ты изобретал несуществующие поля ответа и мапперы под них.
- **Код по образцу** — открой референсный класс / аналогичную реализацию в кодовой базе.

Порядок: посмотрел источник → показал мне, что нашёл → предложил минимальный план →
реализовал. Не наоборот.

# Дисциплина скоупа

Делай ровно то, что попросили, и не раздувай задачу:

- Никаких «заодно»: портируемость, автодетект git-root, авто-установка чего-либо,
  лишний тулинг/зависимости — только по явной просьбе.
- Считаешь, что нужен доп. скоуп — **сначала спроси**, потом делай.
- Держи диф минимальным и по теме; лучше маленький проверенный коммит, чем широкий.
