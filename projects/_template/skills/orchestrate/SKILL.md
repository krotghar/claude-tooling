Пользователь ведёт задачу в режиме оркестратора. Аргументы вызова:

<arguments>
$ARGUMENTS
</arguments>

Основной чат здесь — **оркестратор**: разбирается в задаче, раздаёт работу субагентам,
читает их результаты и приносит пользователю вопросы, на которые нет ответа в постановке.
Код сам не пишет и сборки/тесты сам не гоняет — кроме быстрого пути.

## Быстрый путь

Полный конвейер (исследование бага, планировщик, одобрение плана, ревью) на мелочи стоит
дороже самой правки: прогоны «делай напрямую» занимали 20–31 минуту против 74–168 у
полных (замер 2026-10-15…22). Поэтому в фазе 0, если задача подходит, **сам предложи
быстрый путь** одной строкой вместе с остальными вопросами фазы 0 — решение за
пользователем. Пользователь может и сам попросить («делай напрямую», «без конвейера»).

Подходит, когда всё сразу: один модуль и немного файлов; что менять, понятно из
постановки, скрина, макета или документа задачи (доработка после QA, сепаратор, отступ,
текст); нет продуктовых или дизайнерских развилок.

Как идёт — **всё делает оркестратор сам, без субагентов; максимум — `verifier`**:
1. Фаза 0 — как обычно (ветка, документ задачи, вики).
2. Ни `bug-investigator`, ни планировщика, ни исполнителя, ни ревьюера. `plan.md` и
   WIP-коммиты не заводятся.
3. Оркестратор сам сверяется с источником истины (макет, референсный класс, прецедент в
   git) и сам правит код — правила кодстайла CLAUDE.md проекта те же.
4. Проверка — `verifier` (сборка/тесты по затронутым модулям); если хватает глаз на
   диф — можно и без него. Сборки и тесты сам оркестратор не гоняет. Ревью и проверка
   запуском приложения — только по просьбе пользователя.
5. Завершение — как обычно; материал для `save-task-context` — сама сессия.

Сошёл с быстрого пути — всплыл вопрос не на одну строку, правка расползлась на несколько
модулей, понадобилась проверка запуском приложения — скажи пользователю и переходи на полный
конвейер с той фазы, где остановились.

## Требования из аргументов

В аргументах, кроме самой задачи (номер и/или описание), могут быть требования и
рекомендации пользователя: на что опираться, чего не трогать, как вести процесс. Они
приоритетнее дефолтов этого скилла (модели, состав фаз, WIP-коммиты, когда показывать план).

- Впиши их **дословно** в раздел «Требования пользователя» `plan.md` — так их видят все
  роли. Планировщику передай их ещё и в промпте.
- Требования к самому процессу (без ревью, другая модель исполнителя, что ещё прогнать
  `verifier`) выполняет оркестратор.
- Требование противоречит CLAUDE.md проекта или непонятно, к чему относится, — спроси в
  фазе 0 вместе с остальными пробелами.

## Гигиена контекста оркестратора

Можно читать самому: документ задачи, вики, постановку/макет в объёме, нужном для
понимания, план, журнал исполнения, `git status --short`, `git diff --stat`, точечные
куски дифа, если без них не принять решение.

Нельзя: читать код пачками «чтобы разобраться», писать код (кроме быстрого пути),
запускать сборки и тесты. Нужно
исследование — это работа планировщика или отдельного `Explore`-агента.

## Рабочий каталог

`<scratchpad>/orchestrate/<номер или kebab-тема>/`, где `<scratchpad>` — scratchpad-каталог
сессии из системного промпта. Там живут:

- `plan.md` — план (пишет оркестратор со слов планировщика) + разделы «Требования
  пользователя» и «Решения по ходу» (пишет оркестратор) + раздел «Журнал исполнения»
  (пишет исполнитель).
- `investigation.md` — отчёт `bug-investigator` (только для бага, фаза 0.5).
- `bug-investigation/` — его доказательства (скриншоты, логи, вывод команд).

Передача между ролями — **только через этот файл**, не пересказом в промпте: пересказ
теряет детали, файл читают все роли одинаково. Абсолютный путь к `plan.md` передавай
каждому субагенту.

## Промежуточные коммиты

Перед каждым этапом, где субагент может менять файлы, оркестратор сам делает
WIP-коммит, чтобы откат шёл к известной точке, а не «обратной правкой по памяти».
Такие этапы: заход исполнителя (первый и каждая доработка через `SendMessage`) и прогон
`regression-checker`. Для этапов, которые основной checkout не меняют (исследование бага,
план, ревью, `verifier`), коммит не нужен.

- **База.** До первого WIP-коммита запиши `git rev-parse HEAD` в «Решения по ходу» плана:
  от неё потом сквош.
- **Дерево чистое** — коммитить нечего, этап запускается как есть.
- **Что добавлять.** Только файлы задачи из `git status --short`, поимённо (`git add
  <пути>`), без `-A`/`.`. Файл вне плана в статусе — сначала разберись, откуда он.
- **Сообщение.** `WIP <перед чем>`, например
  `WIP перед regression`. Без описания и без `Co-Authored-By`.
- **Уведомить.** О каждом WIP-коммите сообщи пользователю в том же ответе: хэш и заголовок.
- **Не пушить.** WIP-коммиты живут только локально до сквоша.
- **Субагенты не коммитят**: запрет `git commit` в их контрактах остаётся.
- **Откат порчи.** Смотри `git diff` против последнего WIP. Вернуть файл к WIP
  (`git checkout <wip> -- <путь>`) можно только с разрешения пользователя.

## Фаза 0. Ориентирование (сам)

0. Ветка задачи — по правилу «Ветка под задачу» из CLAUDE.md проекта, до любых
   правок и WIP-коммитов. Правила нет — спроси, от чего и как назвать ветку.
1. Номер задачи → `tasks/pages/<номер>.md` (и связанные), если есть.
2. `wiki/index.md` → подходящие страницы.
3. Постановка: тикет / текст пользователя; требования из аргументов отдели от задачи.
   Пробелы, видные уже сейчас (нет макета, неясно
   поведение в граничном случае, неизвестно, нужен ли фича-флаг), — спроси пользователя **до**
   планирования, одним сообщением.
4. Тип: **баг** или **задача** — по типу тикета в трекере или со слов пользователя.
   Неясно — спроси вместе с пробелами из п. 3. Баг → фаза 0.5, задача → сразу фаза 1
   (или быстрый путь, см. выше).

## Фаза 0.5. Исследование бага (агент `bug-investigator`, только для бага)

Планировщик работает только на чтение и баг не воспроизведёт, поэтому до плана баг
воспроизводит и ищет первопричину отдельный агент — запуском и экспериментами в своём
воркtree. Основной checkout он не меняет.

В промпт: постановку целиком, требования пользователя дословно, ответы из фазы 0, пути
прочитанных страниц вики/документа задачи, абсолютный путь к
`<рабочий каталог>/investigation.md` — туда он пишет отчёт, «стадия 1 (триаж)».

Агент работает в две стадии (см. его п. 0): сначала триаж «повторяется ли и стоит ли
заниматься», потом — по решению пользователя — первопричина. Спрашивают «что там так
долго» — отвечай по разделу «Ход» в `investigation.md`, агента не дёргай.

По статусу после стадии 1:

- **ТРИАЖ: …** — покажи пользователю коротко: воспроизводится ли, где (предварительно),
  гипотезы, сколько займёт стадия 2. **Жди решения**: копать дальше → `SendMessage` тому
  же агенту «стадия 2» (контекст у него есть, новый агент перечитывал бы всё заново);
  не чинить → закрыть задачу (`save-task-context`), удалить воркtree агента (см. ниже);
  чинить по гипотезе без стадии 2 → фаза 1 с отчётом триажа. Решение → «Решения по ходу».

По финальному статусу (после стадии 2 или сразу, если причина подтвердилась на стадии 1):

- **ВОСПРОИЗВЕДЁН** — покажи пользователю коротко: первопричину, уровень доказательства и
  уверенность. Дальше фаза 1 без ожидания одобрения: план всё равно ждёт одобрения.
- **ВОСПРОИЗВЕДЁН, ПРИЧИНА НЕ УСТАНОВЛЕНА**, **НЕ ВОСПРОИЗВЕДЁН**, **НЕ УСТАНОВЛЕНО** —
  к пользователю: что сделано, что не вышло, варианты (дать недостающее и перезапустить
  через `SendMessage` тому же агенту, планировать по гипотезам, закрыть задачу).
  **Жди решения.** Решение → «Решения по ходу».
- Открытые вопросы из отчёта — пользователю вместе со статусом.

Сам проверь `git worktree list` после финального статуса или решения «стадию 2 не
делаем»: `*-research-bug-*` не должно остаться. Остался — удали
(`git worktree remove --force <путь>` + `git worktree prune`) и упомяни пользователю.
После ТРИАЖ, пока решение не принято, воркtree агента остаётся — это нормально.

## Фаза 1. План (субагент `Plan`, `model: "opus"`)

Промпт планировщику должен содержать: постановку целиком, требования пользователя из
аргументов дословно, ответы пользователя из фазы 0, список прочитанных страниц
вики/документа задачи (пути), для бага — путь к `investigation.md` и решения из фазы 0.5,
и требования:

- Сверяться с источником истины (макет через Figma MCP, реальный JSON/модель данных,
  референсная реализация в коде), а не планировать по памяти. В плане указать, **что
  именно сверено** (файл, node, класс).
- Скоуп — ровно постановка; всё «заодно» — в раздел «Вне скоупа», не в шаги.
- Для бага: опираться на `investigation.md`, расследование не повторять — только
  проверить то, на чём строится фикс. Падающий тест из отчёта взять в шаги, а
  проверку запуском после фикса — в «Проверку».
- Вернуть план строго в формате ниже.

```markdown
# <номер> <заголовок>

## Цель
## Требования пользователя
## Сверено с источниками
## Шаги
1. <модуль/файл> — что сделать. Достаточно конкретно, чтобы исполнитель не угадывал.
## Вне скоупа
## Проверка
Модули для сборки/тестов; нужна ли regression-проверка и для какого фикса; какие тесты
добавить/поправить; нужна ли проверка поведения запуском приложения/CLI — пункты (какое
наблюдение что значит) и предусловия (флаги/конфиг, авторизация, тестовые данные).
## Открытые вопросы
Вопрос → варианты → рекомендация планировщика.
## Решения по ходу
## Журнал исполнения
```

Дальше: запиши ответ в `plan.md`, покажи пользователю план (коротко: шаги, вне скоупа,
открытые вопросы). **Жди одобрения.** Ответы на открытые вопросы и правки пользователя
впиши в план сам (мелочь) или отдай планировщику через `SendMessage` (переделка).

## Фаза 2. Исполнение (субагент `general-purpose`, `model: "sonnet"`)

Промпт исполнителю — путь к `plan.md` и контракт ниже дословно:

> Ты исполнитель. Реализуй план из `<путь>/plan.md` — только разделы «Шаги»,
> «Требования пользователя» и «Решения по ходу», ничего сверх. Перед работой прочитай CLAUDE.md проекта; для тестов
> подгрузи скилл `unit-tests` через инструмент Skill.
>
> **Не угадывай.** Если план не отвечает на вопрос (поле не нашлось в ответе API, в
> макете не то, что в плане, референсный класс устроен иначе, шаг противоречит коду) —
> остановись, допиши вопрос в «Журнал исполнения» и верни статус BLOCKED. Сделанное до
> этого не откатывай.
>
> Можно: править файлы по плану, быструю проверку компиляции по затронутым модулям —
> командой из раздела Commands в CLAUDE.md проекта (каждую команду один раз; упало —
> читай ошибку, а не перезапускай).
> Нельзя: `git commit`, `git checkout`/`restore`/`reset`/`clean`/`stash` в любой форме,
> линт, полная сборка проекта, правки вне плана.
>
> Всё, что отклонилось от плана (и почему), пиши в «Журнал исполнения» по ходу.
>
> Верни:
> - Статус: DONE | BLOCKED
> - Изменённые файлы
> - Отклонения от плана
> - Для BLOCKED: вопрос → варианты → твоя рекомендация
> - Результат проверки компиляции (дословно ошибка, если упало)

Запомни ID исполнителя: все дальнейшие правки идут **ему же** через `SendMessage` — у него
уже есть контекст сделанного.

**BLOCKED.** Если ответ однозначно следует из плана, CLAUDE.md или вики — ответь сам и
впиши в «Решения по ходу». Если это новое решение (продуктовое, по дизайну, по скоупу) —
неси пользователю: вопрос, варианты, рекомендация. Ответ → «Решения по ходу» →
`SendMessage` исполнителю «продолжай, решение в плане».

**DONE.** Сам глянь `git status --short` и `git diff --stat`: список файлов совпадает с
отчётом, нет лишних `.orig`/`.bak`, нет файлов вне плана. Отчёт субагента — не
доказательство.

## Фаза 3. Верификация и ревью (параллельно, одним сообщением)

1. `verifier` — модули и проверки из раздела «Проверка» плана, кроме мутаций. Файлы он
   не меняет. В промпт: «Не компилируется или падает — пришли точный текст ошибки, чинить
   не надо». Команды сборки и тестов — из раздела Commands в CLAUDE.md проекта.
2. `reviewer` — на текущий диф, с путём к `plan.md` (чтобы сверял с намерением
   и требованиями пользователя, а не только со стилем).

Сведи результат для пользователя: статус проверок, находки ревью по серьёзности.
**Находки не отдавай в работу без решения пользователя**, даже очевидные.

**Проверка поведения** — если план требует проверки запуском приложения/CLI (раздел
«Проверка»), после зелёного `verifier`: проверь запуском так, как описано в CLAUDE.md
проекта (поручи исполнителю через `SendMessage`: пункты проверки и предусловия из
плана, файлы не менять); в CLAUDE.md способа запуска нет — отдай пункты пользователю (какое наблюдение что
значит) и жди его результата. Итог по пунктам — в «Решения по ходу». Неожиданное
(падения, баги вне списка) — пользователю, в работу без его решения не отдавай.

**Regression-мутации** — если план их требует, отдельным этапом после зелёного
`verifier` и после доработок по ревью (параллельно с ревью нельзя: ревьюер прочитает
мутированный файл). Перед этапом — WIP-коммит. Агент — `regression-checker`, в промпт:
путь к `plan.md`, список мутаций с ожидаемыми тестами, фильтр тестов, хэш WIP. После
прогона сам проверь `git status --short` и `git diff --quiet` против WIP. В отчёте
сверь: у каждой мутации есть имена упавших тестов, среди них целевой; сомнительный
результат (мутация BLOCKED, вердикт расходится с ожиданием без объяснения) — перепрогон
этой мутации через `SendMessage` тому же агенту.

## Фаза 4. Доработка

Одобренные пункты → «Решения по ходу» → `SendMessage` исполнителю. Потом снова
`verifier` (без права правок) по затронутым модулям; если правки задели проверенное
запуском — повтори проверку поведения по затронутым пунктам (как в фазе 3); повторное ревью — только если пользователь попросит или
правки существенные.

## Завершение

Задача готова (всё по плану сделано и проверено, или пользователь сказал «готово» /
«пушь») — доведи её до конца сам, не спрашивая по шагам: сквош от базы из
«Решений по ходу», ребейз, пуш, `save-task-context` (материал — «Решения по ходу» и
журнал исполнения из `plan.md`), артефакт-отчёт, ссылка на MR/PR. Пользователь просит
запушить незаконченное — WIP-коммит и пуш, без отчёта и MR/PR.
