# Правила написания Unit-тестов

При написании или редактировании Unit-тестов строго соблюдай следующие стандарты, принятые в проекте.

Первоисточник — командная вика проекта, раздел про Unit-тесты (если есть). Расходится
этот файл с викой — права вика.

## 1. Стек и инициализация

- Тестовый фреймворк, библиотеки моков/стабов и общие базовые классы/хелперы
  инициализации — **дописываются в проекте** (этот раздел заполняется под стек).
- Пока не дописано — бери то, что уже используется в соседних тестах модуля, и
  не тащи новую тестовую библиотеку без согласования.
- Не меняй видимость продакшен-кода ради теста (не открывай приватное, не
  добавляй методы «только для тестов»).
- **Никаких вспомогательных методов-фабрик и дополнительных классов для тестов**,
  если проект не договорился об ином: нужные варианты входных данных (пустой /
  нулевой / заполненный) — именованными значениями уровня тестового класса/файла.

## 2. Структура теста и именование

- Имя теста описывает условие и ожидаемый результат: `WHEN [действие] EXPECT [результат]`.
  Конкретная форма записи (с учётом ограничений языка на имена) — дописывается
  в проекте; новые тесты называй как соседние.
- Не используй в имени слово `FAILED` и номера («test1», «case2»).
- Тест делится комментариями на три блока:

  ```
  // Prepare
  ...
  // Do
  ...
  // Check
  ...
  ```

## 3. Правила проверок

- Один тест — один логический assert.
- **Проверка взаимодействий** (что зависимость вызвана нужное число раз и
  лишних вызовов нет) делается в том же тесте, вторым assert'ом не считается и
  в отдельный тест не выносится.
- Сравнение целых объектов: при маппинге моделей сравнивай всю ожидаемую модель
  одним сравнением, а не отдельными полями.
- Всегда используй переменные с именами `expected` и `actual` в проверках.
- Для простых структур данных используй реальные объекты, а не моки.
- Строгое соответствие типов: если метод возвращает конкретный тип коллекции или
  значения, в ожидаемой модели используй его же.
- Тест должен падать без проверяемой правки: если удалить или сломать
  тестируемый код, а тест остаётся зелёным — проверка ничего не стоит.

## 4. Асинхронность, время и стабы

- Асинхронный код и потоки данных тестируй средствами тестового фреймворка
  (виртуальное время, тестовый планировщик), а не реальными задержками и `sleep`.
- Не подгоняй таймауты и шаги виртуального времени «с запасом», чтобы тест позеленел.
- Тест детерминирован: никаких зависимостей от текущего времени, случайных чисел,
  сети и порядка выполнения других тестов — всё это подменяется.
- Проверяй вызовы вложенных зависимостей только на один уровень вниз.
- Стаб не должен делать проверку слепой: стаб обёртки, возвращающий свой же
  аргумент, превращает обёртку в тождество, и тест зеленеет даже при её полном
  удалении. Стаб возвращает **отличимое** значение.

## 5. Игнорирование и запуск тестов

- Отключённый тест — штатным механизмом фреймворка с обязательным указанием
  причины или номера задачи (`PROJ-123`).
- Команда запуска — из раздела Commands в `CLAUDE.md` проекта.
